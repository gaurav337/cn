## 2.3 Physical Encoding: Manchester vs Differential Manchester

```
Standard NRZ: High = 1, Low = 0.
Flaw: Long runs of 0s or 1s cause clock drift (receiver desynchronizes).
```

### Manchester Encoding (IEEE 802.3 standard)
- There is **always a transition in the exact middle of every bit interval** (provides self-clocking).
- **Bit 0**: Transition from **High to Low** ($\downarrow$) (or Low-to-High depending on convention; IEEE 802.3 defines Low-to-High for 0 and High-to-Low for 1).
- **Bit 1**: Transition from **Low to High** ($\uparrow$).

### Differential Manchester Encoding (Token Ring 802.5)
- Transition in the middle of every bit is used **solely for clocking**.
- The bit value is determined by the **transition at the START of the bit period**:
  - **Bit 0**: Transition at the **beginning** of the bit interval.
  - **Bit 1**: **No transition** at the **beginning** of the bit interval.
- *Advantage*: Polarity insensitive (if copper wires are swapped, data is still correctly decoded).

```
Bit:             1            0            0            1
        +-----+      +-----+      +-----+            +-----+
Signal: |     |      |     |      |     |            |     |
        +     +------+     +------+     +------------+     +------
             (No inv)     (Inverted)   (Inverted)   (No inv at boundary)
```

## 2.4 Ethernet Frame Anatomy & The "Why 64-Byte Minimum Frame?" Rule

```
+-----------+-----+---------------+---------------+-----------+--------------------+---------+
| Preamble  | SFD | Dest MAC (DA) | Src MAC (SA)  | Type/Len  | Data (Payload)     | CRC/FCS |
|  7 Bytes  | 1 B |    6 Bytes    |    6 Bytes    |  2 Bytes  |  46 - 1500 Bytes   | 4 Bytes |
+-----------+-----+---------------+---------------+-----------+--------------------+---------+
|<-- Physical Layer Header ------>|<---------------- Data Link Layer ------------------------->|
```

- **Preamble (7 Bytes)**: Alternating bits `10101010...` to allow receiver circuitry to synchronize its clock.
- **SFD (Start Frame Delimiter, 1 Byte)**: Pattern `10101011` indicating frame start.
- **EtherType (2 Bytes)**: `0x0800` for IPv4, `0x0806` for ARP.
- **Payload**: Minimum 46 Bytes, Maximum 1500 Bytes (Maximum Transmission Unit - MTU).
- **FCS (Frame Check Sequence, 4 Bytes)**: CRC-32 polynomial over DA, SA, Type, Data.

### The 64-Byte Minimum Frame Proof (Professor's Favorite Theory Question)
**Why must the minimum Ethernet frame size be 64 bytes (46B data + 18B header/trailer)?**

In CSMA/CD, a transmitting station must be able to detect a collision *before it finishes transmitting the frame*. If a station finishes transmission before the collision signal returns, it will assume the transmission succeeded, failing to retransmit!

$$\text{Transmission Time } (T_{tx}) \ge 2 \times \text{Propagation Delay } (T_{prop})$$
$$\frac{L_{min}}{\text{Bandwidth } (R)} \ge 2 \times \frac{\text{Distance } (d)}{v}$$
$$L_{min} \ge 2 \times T_{prop} \times R = \text{Round Trip Time (RTT)} \times R$$

For original 10 Mbps Ethernet over a maximum network diameter of 2.5 km with repeaters:
$$2 \times T_{prop} \approx 51.2\ \mu\text{s}$$
$$L_{min} = 51.2\ \mu\text{s} \times 10\text{ Mbps} = 512\text{ bits} = \mathbf{64\text{ Bytes}}$$
Since headers and FCS take $6 + 6 + 2 + 4 = 18\text{ Bytes}$, minimum payload $= 64 - 18 = \mathbf{46\text{ Bytes}}$.

## 2.5 CSMA/CD & Binary Exponential Backoff Algorithm

When two nodes transmit simultaneously, signals collide.
1. Nodes abort transmission immediately upon detecting collision.
2. They transmit a 32-bit or 48-bit **Jamming Signal** so all stations detect the collision.
3. Both stations invoke the **Truncated Binary Exponential Backoff Algorithm**:
   - Let $k$ be the collision number ($k = \min(\text{attempts}, 10)$).
   - Choose a random integer $r$ from the set $\{0, 1, 2, \dots, 2^k - 1\}$.
   - Wait $r \times \text{Slot Time}$ ($51.2\ \mu\text{s}$) before attempting retransmission.
   - If collision persists after 16 attempts ($k=16$), abort and report error to upper layer.

## 2.6 Transparent Bridging & Self-Learning Switch Tables

A Layer-2 Switch maintains a **MAC Address Table** (Content Addressable Memory - CAM):
$$\text{[Port Number} \mid \text{MAC Address} \mid \text{VLAN ID} \mid \text{Aging Timer]}$$

### Switch Forwarding & Learning Algorithm:
When a frame arrives at Port $P_{in}$ with Source MAC $S$ and Destination MAC $D$:
1. **Learn**: Examine Source MAC $S$. If not present or updated, map $S \to P_{in}$.
2. **Lookup Destination**: Check if Destination MAC $D$ exists in the CAM table:
   - **Case 1 (Known Unicast)**: If $D$ is mapped to port $P_{out}$ (and $P_{out} \neq P_{in}$), forward frame directly out of port $P_{out}$. If $P_{out} == P_{in}$, drop (filter) frame.
   - **Case 2 (Unknown Unicast / Broadcast)**: If $D$ is not in the table or is `FF:FF:FF:FF:FF:FF`, **Flood** the frame out of all ports belonging to the same VLAN *except* $P_{in}$.

# 3. MODULE 2: VLANS & ROUTER-ON-A-STICK (EXAM FAVORITE)

## 3.1 Broadcast Domains & Why VLANs Are Needed
A standard 24-port L2 switch forms **1 single Broadcast Domain** and **24 Collision Domains**.
When a department demands breaking 24 nodes into two isolated groups of 12 nodes without purchasing extra switches or adding physical router ports, **VLANs (Virtual Local Area Networks)** are used.

```
+-------------------------------------------------------------------------------+
|                       PHYSICAL 24-PORT SWITCH S                               |
|   [Ports 1 - 12: Assigned to VLAN 10]   [Ports 13 - 23: Assigned to VLAN 20]  |
|               (Subnet 1)                             (Subnet 2)               |
|                                                                               |
|             Port 24: Configured as TRUNK PORT (Carries both VLANs)            |
+---------------------------------------+---------------------------------------+
                                        | (802.1Q Trunk Link)
                                        v
                            [Router R: Interface Fa0/0]
                              - Sub-interface Fa0/0.10 (Gateway for VLAN 10)
                              - Sub-interface Fa0/0.20 (Gateway for VLAN 20)
```

## 3.2 Access Ports vs Trunk Ports & IEEE 802.1Q Tagging
- **Access Port**: Connected to end-hosts (PCs, printers). End hosts are unaware of VLANs. Frames traveling on access links are **standard untagged Ethernet frames**.
- **Trunk Port**: Connected between switches or between switch and router. Carries traffic for multiple VLANs simultaneously.
- **IEEE 802.1Q Header (4 Bytes)** inserted between Source MAC and EtherType:
  - **TPID (Tag Protocol Identifier, 2 Bytes)**: `0x8100`
  - **TCI (Tag Control Information, 2 Bytes)**:
    - Priority: 3 bits
    - CFI/DEI: 1 bit
    - **VLAN ID (VID): 12 bits** (supports $2^{12} = 4096$ VLANs, 1 to 4094 usable).

## 3.3 Router-on-a-Stick Configuration & Step-by-Step Packet Tracing
Suppose:
- **VLAN 10**: Subnet `20.20.20.0/28` (Ports 1-4). PC1 on Port 1 has IP `20.20.20.2`, MAC `PC1-H`. Gateway is `20.20.20.1`.
- **VLAN 20**: Subnet `20.20.20.48/28` (Ports 11-14). PC2 on Port 11 has IP `20.20.20.50`, MAC `PC2-H`. Gateway is `20.20.20.49`.
- **Trunk Link**: Port 24 connected to Router interface `Fa0/0`.
  - Router sub-interface `Fa0/0.10`: IP `20.20.20.1/28`, Encapsulation dot1Q 10, MAC `R-fa0-H`.
  - Router sub-interface `Fa0/0.20`: IP `20.20.20.49/28`, Encapsulation dot1Q 20, MAC `R-fa0-H`.

### Step-by-Step Packet Trace: PC1 sends packet P to PC2
1. **At PC1**: PC1 compares destination IP `20.20.20.50` with its own subnet mask `/28` (`255.255.255.240`). Since network IDs differ, PC1 knows PC2 is on a **remote subnet**. PC1 sends packet to its Default Gateway `20.20.20.1`.
   - PC1 looks up ARP cache for `20.20.20.1` $\to$ gets `R-fa0-H`.
   - PC1 outputs frame to Port 1:
     $$\text{[Src MAC: PC1-H | Dst MAC: R-fa0-H | Src IP: 20.20.20.2 | Dst IP: 20.20.20.50]}$$
2. **At Switch S (Port 1)**:
   - Switch receives frame on Port 1 (member of VLAN 10).
   - Looks up destination MAC `R-fa0-H` in CAM table for VLAN 10 $\to$ finds Port 24 (Trunk).
   - **Switch inserts 802.1Q Tag (VLAN ID = 10)** into frame.
   - Transmits tagged frame on Port 24:
     $$\text{[Src MAC: PC1-H | Dst MAC: R-fa0-H | \textbf{VLAN: 10} | Src IP: 20.20.20.2 | Dst IP: 20.20.20.50]}$$
3. **At Router R (Sub-interface Fa0/0.10)**:
   - Router strips 802.1Q Tag (VLAN 10) and hands packet to sub-interface `Fa0/0.10`.
   - Strips L2 Ethernet header, examines Destination IP `20.20.20.50`.
   - Looks up routing table: `20.20.20.48/28` is directly connected via `Fa0/0.20`.
   - Looks up ARP cache for `20.20.20.50` $\to$ gets `PC2-H`.
   - Encapsulates into new Ethernet frame, **adds 802.1Q Tag (VLAN ID = 20)**.
   - Transmits back out `Fa0/0` towards Switch:
     $$\text{[Src MAC: R-fa0-H | Dst MAC: PC2-H | \textbf{VLAN: 20} | Src IP: 20.20.20.2 | Dst IP: 20.20.20.50]}$$
4. **At Switch S (Port 24)**:
   - Switch receives frame tagged with VLAN 20.
   - Looks up destination MAC `PC2-H` in CAM table for VLAN 20 $\to$ finds Port 11 (Access port).
   - **Switch strips the 802.1Q VLAN Tag**.
   - Forwards standard untagged Ethernet frame to PC2:
     $$\text{[Src MAC: R-fa0-H | Dst MAC: PC2-H | Src IP: 20.20.20.2 | Dst IP: 20.20.20.50]}$$

# 4. MODULE 3: IP ADDRESSING, SUBNETTING, VLSM & SUPERNETTING

## 4.1 Finding Starting Network Address Given an Arbitrary IP and Prefix Length
A common exam prompt states:
*"An ISP allocates a /21 network. One IP is 20.20.69.0/21. Find the starting address of the network."*
Or: *"Allocated /23 network, one address is 20.20.11.0/23. Find starting address."*

### The Systematic Method:
1. Identify which octet contains the subnet boundary:
   - $/24$ to $/32 \implies$ 4th octet
   - $/16$ to $/23 \implies$ 3rd octet
   - $/8$ to $/15 \implies$ 2nd octet
2. For `/23`: $23 = 16 + 7$. Boundary is in 3rd octet. Subnet mask $= 255.255.254.0$.
   - Look at 3rd octet of `20.20.11.0`: decimal `11` in binary is `00001011`.
   - Network mask has 7 bits in 3rd octet: `11111110`.
   - Bitwise AND: `00001011` AND `11111110` = `00001010` (decimal **10**).
   - **Starting Address = `20.20.10.0/23`**.
   - Total addresses $= 2^{32-23} = 2^9 = 512$ addresses (range `20.20.10.0` to `20.20.11.255`).

3. For `/21`: $21 = 16 + 5$. Boundary is in 3rd octet. Subnet mask $= 255.255.248.0$.
   - Block size in 3rd octet $= 2^{8-5} = 2^3 = 8$.
   - Multiples of 8 in 3rd octet: $0, 8, 16, 24, \dots, 64, 72$.
   - For decimal `69`: $64 \le 69 < 72$.
   - **Starting Address = `20.20.64.0/21`**.
   - Total addresses $= 2^{32-21} = 2^{11} = 2048$ addresses (range `20.20.64.0` to `20.20.71.255`).

## 4.2 Step-by-Step VLSM Allocation Algorithm
**Golden Rule of VLSM**: Always sort requirements in **strictly descending order** of host count. Allocate the largest subnets first to prevent fragmented address blocks!

### Required Block Size Formula:
For $H$ usable hosts, required power-of-two block size $N = 2^h$ such that:
$$2^h - 2 \ge H \quad (\text{or } 2^h \ge H + 2)$$
Prefix length $= 32 - h$. Subnet mask has $32-h$ ones.

### Complete Reference Table for Subnet Masks:
```
+---------+--------------+--------------+------------------+
| Prefix  | Host Bits(h) | Total Addr   | Subnet Mask      |
+---------+--------------+--------------+------------------+
| /24     | 8            | 256          | 255.255.255.0    |
| /25     | 7            | 128          | 255.255.255.128  |
| /26     | 6            | 64           | 255.255.255.192  |
| /27     | 5            | 32           | 255.255.255.224  |
| /28     | 4            | 16           | 255.255.255.240  |
| /29     | 3            | 8            | 255.255.255.248  |
| /30     | 2            | 4 (2 hosts)  | 255.255.255.252  |
+---------+--------------+--------------+------------------+
```

## 4.3 The "Infinite Ping-Pong Routing Loop" Trap & How to Fix It
*(Appears in 2024 & 2025 Mid Sem Papers)*

```
[Institute Host n2] ---> [Core Switch Rc] ---> [Gateway Router Rg] <=========> [ISP Router RISP]
                                                                  (Ping-Pong
                                                                   Routing Loop!)
```

### Scenario:
1. Institute is assigned `20.20.10.0/23`.
2. Active departments use addresses up to `20.20.10.223`.
3. Addresses in `20.20.11.0/24` are currently **unallocated/empty**.
4. An internal host $n_2$ sends a packet to an unassigned IP: `20.20.11.200`.

### The Catastrophic Loop:
1. $n_2$ forwards to Core switch $R_C$.
2. $R_C$ finds no specific route for `20.20.11.0/24` in its table. It matches its **Default Route (`0.0.0.0/0`)** pointing to Gateway Router $R_g$.
3. $R_g$ also finds no specific route. It matches its **Default Route** pointing to ISP Router $R_{ISP}$.
4. $R_{ISP}$ receives the packet. In $R_{ISP}$'s routing table, the ISP has an **aggregated route**:
   $$\text{Destination: } 20.20.10.0/23 \implies \text{Next Hop: } R_g$$
5. $R_{ISP}$ sends the packet **BACK** to $R_g$!
6. $R_g$ looks at its default route and sends it **BACK** to $R_{ISP}$!
7. The packet bounces between $R_g$ and $R_{ISP}$ until its **TTL (Time to Live) decrements to 0**, consuming valuable WAN bandwidth!

### The Professor's Required Solutions:
1. **Blackhole / Null0 Route (Best Practice)**:
   Configure a static route on Gateway Router $R_g$:
   ```cisco
   ip route 20.20.10.0 255.255.254.0 Null0
   ```
   *Mechanism*: More specific subnets (`/26`, `/27`) match first (Longest Prefix Match). Unallocated IPs within `/23` hit the summary route pointing to `Null0` and are **immediately silently dropped** at $R_g$, preventing the packet from ever reaching $R_{ISP}$!
2. **Access Control List (ACL) Filter**:
   Add an egress ACL on $R_g$ outbound to $R_{ISP}$ denying packets with destination in unallocated blocks (`20.20.11.0/24`).

## 6.1 Demultiplexing: Listening Socket vs Connection Socket
*(Directly tested in Endsem Examination)*

**Question**: *"While sending HTTP request, will TCP SYN message and HTTP GET message be directed to the same socket at the server? Explain."*

**Answer: NO! They are handled by DIFFERENT sockets.**
1. **Passive / Listening Socket (`listenfd`)**:
   - The server creates a listening socket bound to server IP and Port 80:
     $$\text{Tuple: } (*, 80)$$
   - The initial **TCP SYN** packet is directed to this listening socket.
   - The listening socket handles the 3-Way Handshake.
2. **Connected Socket (`connfd`)**:
   - Once the handshake is completed, the OS kernel `accept()` system call creates a **new, dedicated Connection Socket**.
   - This connection socket is bound to the full **4-tuple**:
     $$\text{(Source IP, Source Port, Dest IP, Dest Port)}$$
   - All subsequent packets, including the **HTTP GET** request and HTTP responses, are directed exclusively to this connection socket!
   - *Why?* This allows the server to serve thousands of concurrent clients on the same port 80 simultaneously!

## 7.1 TCP 3-Way Handshake & Ghost Connection Prevention

```
Client                                                  Server
  |                                                       |
  | ------------ 1. SYN (seq=x) ------------------------> | (LISTEN -> SYN-RCVD)
  |                                                       |
  | <----------- 2. SYN-ACK (seq=y, ack=x+1) ------------ |
  |                                                       |
  | ------------ 3. ACK (seq=x+1, ack=y+1) -------------> | (ESTABLISHED)
```

### Why the 3rd ACK is Mandatory (Ghost Connection Prevention):
Suppose an old duplicate SYN packet delayed in the network arrives at the server long after the client has closed.
- If only a 2-way handshake existed, the server would open a connection and allocate memory/resources immediately.
- The client, having never sent this SYN recently, would ignore the server's reply.
- The server would now be stuck with a **"Ghost Connection" (Half-open connection)** wasting kernel memory!
- With the 3-way handshake, the server waits for the 3rd ACK. If client gets SYN-ACK for an unknown session, it replies with **RST (Reset)**, destroying the ghost connection!

## 7.2 TCP Tahoe vs TCP Reno: Congestion Control Evolution

Both protocols operate in phases:
- **Slow Start (SS)**: $cwnd$ starts at $1\text{ MSS}$. Doubles every RTT ($cwnd = cwnd + 1$ per received ACK). Exponential growth.
- **Congestion Avoidance (CA)**: When $cwnd \ge ssthresh$, $cwnd$ grows linearly by $1\text{ MSS}$ per RTT ($cwnd = cwnd + \frac{1}{cwnd}$ per ACK).

```
+---------------------------------------+---------------------------------------+
| Event                                 | TCP Tahoe                             | TCP Reno                              |
+---------------------------------------+---------------------------------------+
| Timeout                               | ssthresh = cwnd / 2                   | ssthresh = cwnd / 2                   |
|                                       | cwnd = 1 MSS                          | cwnd = 1 MSS                          |
|                                       | Enter Slow Start                      | Enter Slow Start                      |
+---------------------------------------+---------------------------------------+
| 3 Duplicate ACKs                      | ssthresh = cwnd / 2                   | ssthresh = cwnd / 2                   |
| (Triple Duplicate ACK)                | cwnd = 1 MSS                          | cwnd = ssthresh + 3 MSS               |
|                                       | Fast Retransmit lost packet           | Fast Retransmit lost packet           |
|                                       | Enter Slow Start                      | Enter Fast Recovery                   |
+---------------------------------------+---------------------------------------+
| Arrival of duplicate ACK in           | N/A (Tahoe doesn't have Fast Recovery)| cwnd = cwnd + 1 MSS                   |
| Fast Recovery                         |                                       | Transmit new packet if allowed        |
+---------------------------------------+---------------------------------------+
| Arrival of NEW ACK                    | Normal Slow Start / CA behavior       | cwnd = ssthresh                       |
| (Deflation)                           |                                       | Enter Congestion Avoidance            |
+---------------------------------------+---------------------------------------+
```

## 7.3 Mathematical Problem: Sequence Number Wraparound Time
*(Guaranteed IIT/NIT Exam Numerical)*

**Problem**: *Given Bandwidth $B = 20\text{ Mbps}$ (where $1\text{ Megabit} = 2^{20}\text{ bits}$), TCP uses 32-bit sequence numbers. How long will it take for sequence numbers to wrap around?*

### Solution:
- Sequence numbers count **bytes**, not packets!
- Total sequence numbers $= 2^{32}\text{ bytes}$.
- Total bits before wraparound $= 2^{32} \times 8\text{ bits} = 2^{35}\text{ bits}$.
- Data rate $R = 20 \times 2^{20}\text{ bits/second}$.

$$\text{Time to wraparound } (T_{wrap}) = \frac{\text{Total Bits}}{\text{Rate}} = \frac{2^{35}\text{ bits}}{20 \times 2^{20}\text{ bps}} = \frac{2^{15}}{20} = \frac{32768}{20} = \mathbf{1638.4\text{ seconds}} \approx \mathbf{27.3\text{ minutes}}$$

### If Bandwidth is 1 Gbps or 10 Gbps:
At 10 Gbps ($10 \times 10^9$ bps $\approx 1.25 \times 10^9$ Bps):
$$T_{wrap} = \frac{2^{32}\text{ bytes}}{1.25 \times 10^9\text{ Bps}} \approx \mathbf{3.43\text{ seconds}}!$$
Because Internet Maximum Segment Lifetime ($MSL$) is standardized at **120 seconds (2 minutes)**, an old delayed duplicate segment would re-enter the TCP window of a new connection and corrupt data!

### Solution: PAWS (Protection Against Wrapped Sequence Numbers - RFC 1323)
TCP includes the **Timestamps Option** (10 bytes total: 4-byte Timestamp Value `TSval`, 4-byte Timestamp Echo Reply `TSecr`).
- Every TCP segment carries a 32-bit timestamp clock.
- If a segment arrives whose sequence number falls within the window but whose timestamp `TSval` is older than the latest timestamp received for this connection, **it is identified as an old incarnation and dropped**!

## 7.4 Mathematical Problem: TCP Window Scaling Factor
*(Guaranteed IIT/NIT Exam Numerical)*

**Problem**: *Given Bandwidth $B = 20\text{ Mbps}$, $RTT = 100\text{ ms}$. What window scaling factor must be negotiated between sender and receiver for maximum utilization of the link?*

### Solution:
1. **Bandwidth-Delay Product (BDP)**:
   $$\text{BDP} = \text{Bandwidth} \times \text{RTT} = (20 \times 2^{20}\text{ bps}) \times (100 \times 10^{-3}\text{ s}) = 2,097,152\text{ bits} = \mathbf{262,144\text{ Bytes}} = 256\text{ KB}$$
2. **Examine Standard TCP Header Window Field**:
   - The TCP Window field is **16 bits** wide.
   - Maximum unscaled window size $= 2^{16} - 1 = 65,535\text{ Bytes} \approx 64\text{ KB}$.
   - Since $64\text{ KB} < 256\text{ KB}$, the standard window **cannot fill the pipe**, limiting throughput to $\frac{64\text{ KB}}{100\text{ ms}} = 5.24\text{ Mbps}$ (less than 26% efficiency!).
3. **Window Scale Option (RFC 1323)**:
   - Window scaling factor $S$ shifts the 16-bit window left by $S$ bits:
     $$\text{Effective Window} = \text{Window Field} \times 2^S$$
   - We need:
     $$65535 \times 2^S \ge \text{BDP} = 262,144$$
     $$2^S \ge \frac{262,144}{65,535} \approx 4.00006$$
   - For $S = 2$: $65535 \times 4 = 262,140\text{ Bytes}$ (just 4 bytes short).
   - Therefore, choose **$S = 3$** ($2^3 = 8$), which allows a maximum window of $65,535 \times 8 = 524,280\text{ Bytes} > 262,144\text{ Bytes}$.
   - **Scale factor $S = 3$** (shift count $= 3$, multiplier $= 8$).

## 7.6 Adaptive Retransmission: Jacobson’s & Karn’s Algorithms

### Karn’s Algorithm (RFC 6298)
**The Retransmission Ambiguity Problem**: When a segment is retransmitted and an ACK arrives, does the ACK correspond to the original transmission or the retransmission?
- If you guess original: measured RTT is falsely too large.
- If you guess retransmission: measured RTT is falsely too small.
**Karn's Rules**:
1. **Never calculate RTT sample for retransmitted segments!**
2. **Exponential Timer Backoff**: Every time a timeout occurs, double the Retransmission Timeout ($RTO = 2 \times RTO$). Only reset $RTO$ when an ACK arrives for a segment that was sent without retransmission.

### Jacobson's RTT Calculation:
$$\text{EstimatedRTT} = (1 - \alpha) \times \text{EstimatedRTT} + \alpha \times \text{SampleRTT} \quad (\alpha = 0.125)$$
$$\text{DevRTT} = (1 - \beta) \times \text{DevRTT} + \beta \times |\text{SampleRTT} - \text{EstimatedRTT}| \quad (\beta = 0.25)$$
$$RTO = \text{EstimatedRTT} + 4 \times \text{DevRTT}$$

# 9. MODULE 8: ADVANCED NETWORK LAYER & ROUTING PROTOCOLS

## 9.1 Router Architecture & Switching Fabrics (From Network Layer.pptx)
A router performs two primary functions:
1. **Routing (Control Plane)**: Determines end-to-end path taken by packets using routing algorithms (RIP, OSPF, BGP). Runs in software on routing processor (milliseconds timescale).
2. **Forwarding (Data Plane)**: Transfers packet from incoming physical link to appropriate outgoing physical link based on forwarding table. Runs in hardware/ASICs (nanoseconds timescale).

```
+---------------------------------------------------------------------------------+
|                               ROUTER ARCHITECTURE                               |
|                                                                                 |
|                   +---------------------------------------+                     |
|                   |           Routing Processor           | (Control Plane)     |
|                   |     (Routing Protocols: RIP, OSPF)    |                     |
|                   +-------------------+-------------------+                     |
|                                       |                                         |
|  +----------------+                   v                   +-----------------+   |
|  |   Input Port   | ----> +-----------------------+ ----> |   Output Port   |   |
|  | Line -> PHY/L2 |       |    Switching Fabric   |       | Buffer -> Queuing|  |
|  | Lookup & Queue | ----> |  (Memory/Bus/Crossbar)| ----> | Transmission    |   |
|  +----------------+       +-----------------------+       +-----------------+   |
|  (Data Plane)                                                     (Data Plane)  |
+---------------------------------------------------------------------------------+
```

### Components of Router Input & Output Ports:
- **Input Port Functions**:
  1. *Physical Layer*: Line termination and bit-level reception.
  2. *Data Link Layer*: Decapsulation and verification of frame check sequence (CRC).
  3. *Decentralized Lookup & Forwarding*: Hardware lookup of destination IP in forwarding table using **Longest Prefix Match (TCAM - Ternary Content Addressable Memory)**.
  4. *Input Queuing & Head-of-Line (HOL) Blocking*: If the switching fabric is busy, packets queue at input port. A packet at the head of the queue waiting for a busy output port blocks all packets behind it, even if their desired output ports are completely free!
- **Switching Fabric Types**:
  1. *Memory*: Switching under direct control of CPU. Packet copied to system memory and then to output port. Limited by memory bus bandwidth ($B/2$).
  2. *Bus*: Input port transfers packet directly across a shared internal bus to output port without CPU intervention. Bus contention limits throughput (only 1 packet at a time).
  3. *Crossbar (Interconnection Network)*: $2N$ buses connecting $N$ input ports to $N$ output ports via a matrix of fabric switches. Allows multiple packets to be forwarded concurrently as long as their input and output ports are distinct.
- **Output Port Functions**:
  - Buffer management and packet dropping policies (Drop-Tail, RED).
  - Packet scheduling algorithms: **FIFO**, **Priority Queuing**, **Round Robin (RR)**, and **Weighted Fair Queuing (WFQ)**.

## 9.2 IPv4 Datagram Header & Fragmentation/Reassembly Algorithm

### Key Header Fields:
- **Version (4 bits)**: `4` for IPv4.
- **IHL (Internet Header Length, 4 bits)**: Number of 32-bit (4-byte) words. Minimum value is `5` ($5 \times 4 = 20\text{ Bytes}$), maximum is `15` ($15 \times 4 = 60\text{ Bytes}$).

- **Identification (16 bits)**: Unique ID assigned to original datagram; shared by all fragments of the same datagram.
- **Flags (3 bits)**:
  - Bit 0: Reserved (must be 0).
  - Bit 1: **DF (Don't Fragment)**. If set to 1 and packet exceeds MTU, router drops it and sends ICMP Destination Unreachable (Fragmentation Needed).
  - Bit 2: **MF (More Fragments)**. Set to 1 for all fragments except the very last fragment (where MF = 0).
- **Fragment Offset (13 bits)**: Measured in **units of 8 bytes (64 bits)**. Specifies position of fragment's data relative to original payload.
- **Time to Live (TTL, 8 bits)**: Decremented by 1 at every router hop. Prevents infinite looping. When TTL = 0, packet dropped and ICMP Time Exceeded returned.
- **Protocol (8 bits)**: Upper layer protocol (`1` = ICMP, `6` = TCP, `17` = UDP, `89` = OSPF).
- **Header Checksum (16 bits)**: 1's complement sum of header fields only (recomputed at each router because TTL changes).

### Numerical Example: IPv4 Fragmentation
**Scenario**: A 4000-byte IPv4 datagram (20-byte IP header + 3980 bytes payload) arrives at an outgoing link with **MTU = 1500 bytes**.
- Maximum payload per fragment $= 1500 - 20 = 1480\text{ bytes}$.
- Must be a multiple of 8: $1480 / 8 = 185$ (Valid!).
- Total payload to fragment $= 3980\text{ bytes}$.

```
+------------+--------------+---------------+-------+-----------------+---------------------------+
| Fragment   | Total Length | Payload Size  | Flags | Fragment Offset | Offset in 8-byte Units    |
+------------+--------------+---------------+-------+-----------------+---------------------------+
| Frag 1     | 1500 Bytes   | 1480 Bytes    | MF = 1| 0 bytes         | Offset = 0 / 8 = 0        |
| Frag 2     | 1500 Bytes   | 1480 Bytes    | MF = 1| 1480 bytes      | Offset = 1480 / 8 = 185   |
| Frag 3     | 1040 Bytes   | 1020 Bytes    | MF = 0| 2960 bytes      | Offset = 2960 / 8 = 370   |
+------------+--------------+---------------+-------+-----------------+---------------------------+
```
*(All 3 fragments carry identical 16-bit Identification numbers. Reassembly occurs exclusively at the FINAL DESTINATION host, never at intermediate routers!)*

- **Major Architectural Improvements over IPv4**:

1. **Dual Stack**: Routers and hosts run both IPv4 and IPv6 protocol stacks simultaneously. They translate between IPv4 and IPv6 based on DNS lookups.
2. **Tunneling (6to4 / Teredo)**: When two IPv6 nodes communicate across an intervening IPv4 network, the IPv6 datagram is encapsulated as payload inside an IPv4 packet (`Protocol 41` in IPv4 header).
3. **NAT64 / DNS64**: Translates IPv6-only clients to communicate with legacy IPv4-only servers.

## 9.5 Routing Algorithms: Link-State (Dijkstra) vs Distance Vector (Bellman-Ford)

### A. Dijkstra's Link-State Routing Algorithm (OSPF)
- Global algorithm: Every router knows complete network topology and all link costs via Link State Advertisements (LSAs) flooded over the network.
- **Notation**:
  - $c(x,y)$: Link cost from $x$ to $y$ (equals $\infty$ if not direct neighbors).
  - $D(v)$: Current cost of least-cost path from source $u$ to destination $v$.
  - $p(v)$: Predecessor node along path from $u$ to $v$.
  - $N'$: Subset of nodes whose least-cost paths are definitively known.

#### Step-by-Step Algorithm Execution (Source = Node $u$):
```
1. Initialization:
   N' = {u}
   For all nodes v:
     If v is adjacent to u:
        D(v) = c(u,v), p(v) = u
     Else:
        D(v) = infinity

2. Loop:
   Find w NOT in N' such that D(w) is MINIMUM.
   Add w to N': N' = N' U {w}
   Update D(v) for all neighbors v of w NOT in N':
      D(v) = min( D(v), D(w) + c(w,v) )
      If updated, p(v) = w
   Until all nodes are in N'.
```

#### Example Dijkstra SPF Table (Source Node $u$):
Given network: $c(u,x)=1, c(u,v)=2, c(u,w)=5, c(x,v)=2, c(x,y)=1, c(v,w)=3, c(y,w)=2, c(y,z)=2, c(w,z)=5$:

```
+------+--------------+----------+----------+----------+----------+----------+
| Step | N'           | D(v),p(v)| D(x),p(x)| D(w),p(w)| D(y),p(y)| D(z),p(z)|
+------+--------------+----------+----------+----------+----------+----------+
| 0    | {u}          | 2, u     | 1, u     | 5, u     | infinity | infinity |
| 1    | {u, x}       | 2, u     | -        | 5, u     | 2, x     | infinity |
| 2    | {u, x, y}    | 2, u     | -        | 4, y     | -        | 4, y     |
| 3    | {u, x, y, v} | -        | -        | 4, y     | -        | 4, y     |
| 4    | {u, x, y,v,w}| -        | -        | -        | -        | 4, y     |
| 5    | {all}        | -        | -        | -        | -        | -        |
+------+--------------+----------+----------+----------+----------+----------+
```
*Shortest Path Tree constructed from source $u$ yields next-hop forwarding entries.*

### B. Distance Vector Algorithm & Bellman-Ford Equation (RIP)
- Decentralized, iterative, asynchronous algorithm.
- Each router $x$ maintains distance vector $D_x = [D_x(y) : y \in N]$.
- **Bellman-Ford Equation**:
  $$d_x(y) = \min_v \left\{ c(x,v) + d_v(y) \right\}$$
  Where the minimum is taken over all immediate neighbors $v$ of node $x$.
- **Asymmetric Convergence ("Good News Travels Fast, Bad News Travels Slow")**:
  - When link cost decreases (e.g. from 4 to 1), routing tables converge within 2 iterations.
  - When link cost increases or a link breaks, routers exchange stale circular updates resulting in the **Count-to-Infinity Problem**!

## 10.2 UDP Checksum & 12-Byte Pseudo-Header Calculation
UDP provides connectionless, best-effort service with an **8-byte header**:
$$\text{[Source Port (16b) | Destination Port (16b) | Length (16b) | Checksum (16b)]}$$

### UDP Pseudo-Header Construction:
To compute the checksum, UDP prepends a **12-byte Pseudo-Header** containing:
1. Source IP Address (32 bits / 4 bytes)
2. Destination IP Address (32 bits / 4 bytes)
3. Fixed Zero octet (8 bits: `0x00`)
4. Protocol octet (8 bits: `17` = `0x11`)
5. UDP Length field (16 bits: length of UDP header + UDP data)

```
+-----------------------------------------------------------------+
|                    Source IP Address (4 Bytes)                  |
+-----------------------------------------------------------------+
|                 Destination IP Address (4 Bytes)                |
+----------------+----------------+-------------------------------+
|  All 0s (1 B)  | Protocol=17(1B)|      UDP Length (2 Bytes)     |
+----------------+----------------+-------------------------------+
|                      UDP Header + UDP Payload                   |
+-----------------------------------------------------------------+
```
- **Algorithm**:
  1. Divide pseudo-header, UDP header, and payload into 16-bit words (pad odd byte with 0s at end).
  2. Compute 16-bit 1's complement sum (add carry bits back to lowest bit - end-around carry).
  3. Invert all bits (1's complement) and write to Checksum field.
  4. If computed checksum is 0, write all 1s (`0xFFFF`). If checksum not calculated, sender writes `0x0000`.

## 10.3 TCP Connection Termination & The 2*MSL TIME_WAIT State
TCP closes a connection using a **4-Way Handshake**:

```
Client (Active Close)                                   Server (Passive Close)
  |                                                               |
  | ------------ 1. FIN (seq=u) --------------------------------> | (ESTABLISHED -> CLOSE_WAIT)
  |      (FIN_WAIT_1)                                             |
  | <----------- 2. ACK (ack=u+1) ------------------------------- |
  |      (FIN_WAIT_2)                                             |
  |                                                               |
  |                                   [Server finishes data]      |
  | <----------- 3. FIN (seq=v, ack=u+1) ------------------------ | (LAST_ACK)
  |                                                               |
  | ------------ 4. ACK (ack=v+1) ------------------------------> | (CLOSED)
  |      (TIME_WAIT: 2 * MSL)                                     |
  |                                                               |
  v (CLOSED after 2*MSL)
```

### Why the 2*MSL TIME_WAIT State is Mandatory:
1. **Ensure Final ACK Delivery**: If the client's final ACK (packet 4) is lost, the server retransmits its FIN (packet 3). If client had immediately closed, it would reply with `RST`, causing the server to believe an error occurred rather than a clean close!
2. **Prevent Old Duplicate Interference**: $MSL$ is the Maximum Segment Lifetime ($120\text{ seconds}$). Waiting $2 \times MSL$ ($240\text{ seconds}$) guarantees all lingering, delayed duplicate segments from this connection expire in the network before a new connection can reuse the same socket 4-tuple!

## 10.4 TCP Window Dynamics, Delayed ACKs & SACK Options

### A. Sliding Window Edge Movements
- **Window Closes**: Left edge moves to the right when sender receives ACK advancing the acknowledgment number.
- **Window Opens**: Right edge moves to the right when receiver advertises a larger window credit.
- **Window Shrinks**: Right edge moves to the left when receiver decreases advertised window without data being ACKed. **RFC 1122 explicitly discourages window shrinking**, as it causes data previously within the window to become outside, triggering race conditions and packet loss!

### B. TCP ACK Generation Rules (RFC 1122 & RFC 2581)
1. **In-order segment arrived; no other pending ACK**: Delayed ACK timer starts. Wait up to **500 ms** for next segment; if none arrives, send ACK.
2. **In-order segment arrived; one ACK already pending**: Send immediate cumulative ACK acknowledging both segments.
3. **Out-of-order segment arrived (gap detected)**: Send **immediate duplicate ACK** reporting expected sequence number.
4. **Segment arrived that partially or completely fills gap**: Send immediate cumulative ACK.

### C. TCP SACK (Selective Acknowledgement - RFC 2018)
Standard TCP cumulative ACK only reports the contiguous stream received. If packets 1, 3, 4, 5 arrive, sender retransmits 2, but also retransmits 3, 4, 5!
- **SACK Option Format**: Located in TCP options (`Kind = 5`).
- Contains pairs of 32-bit pointers: **[Left Edge, Right Edge]**.
- Maximum of **4 SACK blocks** can be reported in the 40-byte options space.
- Allows receiver to inform sender: *"I have received bytes 3000-4000 and 5000-6000; only retransmit bytes 1000-2999 and 4001-4999."*

## 11.2 Chord Distributed Hash Table (DHT) & Finger Tables

Chord uses consistent hashing (SHA-1) to map both nodes and keys into an $m$-bit circular identifier ring modulo $2^m$.

```
                        Node 0
                   /              \
            Node 28                Node 1
           /                            \
      Node 21         CHORD RING         Node 4
          \           (Modulo 2^m)      /
           \                           /
            Node 18               Node 8
                   \              /
                     Node 14 - Node 9
```

### Chord Rules:
1. **Key Assignment**: Key $k$ is stored at the node whose identifier is $\ge k$, denoted **$successor(k)$**.
2. **Finger Table Construction**: Each node $n$ maintains an $m$-entry Finger Table:
   $$\mathbf{Finger[i] = successor\left((n + 2^{i-1}) \pmod{2^m}\right)} \quad \text{for } 1 \le i \le m$$
3. **Logarithmic Routing**: When searching for key $k$, node $n$ forwards query to the closest predecessor in its finger table that precedes $k$. Halves the remaining distance to target at each step $\implies \mathbf{O(\log N)\text{ routing hops}}$!

### Step-by-Step Numerical Example ($m = 6$, Identifier space $= 0 \text{ to } 63$):
Active nodes present in ring: $\{1, 12, 25, 32, 45, 58\}$.
Let us construct the **Finger Table for Node 12** ($n=12, m=6$):

```
+---+----------------------+--------------------+--------------------+
| i | Formula: n + 2^(i-1) | Target Identifier  | Finger[i] = Succ() |
+---+----------------------+--------------------+--------------------+
| 1 | 12 + 2^0 = 12 + 1    | 13                 | Node 25            |
| 2 | 12 + 2^1 = 12 + 2    | 14                 | Node 25            |
| 3 | 12 + 2^2 = 12 + 4    | 16                 | Node 25            |
| 4 | 12 + 2^3 = 12 + 8    | 20                 | Node 25            |
| 5 | 12 + 2^4 = 12 + 16   | 28                 | Node 32            |
| 6 | 12 + 2^5 = 12 + 32   | 44                 | Node 45            |
+---+----------------------+--------------------+--------------------+
```
- **Lookup Query**: Node 12 seeks key $k = 42$.
  - Node 12 checks its finger table. The largest entry preceding 42 is Finger[5] = Node 32.
  - Node 12 forwards query directly to Node 32!
  - Node 32 looks up key 42 and finds its successor is Node 45. Done in 2 hops!

## Problem 3: Sliding Window GBN vs SR vs TCP Simulation (Scan0028 Exam Paper)

**Statement**:
- $T_{tx} = 1\text{ ms}$, $RTT = 10\text{ ms}$. Window size $W = 5$ (fixed). Sequence numbers $= 0 \text{ to } 15$.
- Sender $S$ sends 5 segments. **The 2nd segment (sequence number 1) is lost on first attempt**.
- All segments successfully received after retransmission of 2nd segment.

### Part (i): Schematic & Transmission Count
- Initial transmission: Sender transmits segments `0, 1, 2, 3, 4`. Segment 1 is dropped.
- **In GBN**:
  - Receiver accepts segment 0, sends ACK 0.
  - When segments 2, 3, 4 arrive, receiver discards them (out of order!) and retransmits ACK 0 three times.
  - At timeout of segment 1, sender window still has `[1, 2, 3, 4, 5]`.
  - Sender must retransmit **ALL 4 remaining packets**: `1, 2, 3, 4`!
  - **Total segments sent by $S$ in GBN $= 5 + 4 = \mathbf{9\text{ segments}}$.**
  - **Total ACKs sent by $R = 1 + 3 + 4 = \mathbf{8\text{ ACKs}}$.**
- **In SR**:
  - Receiver accepts segment 0 (ACK 0), buffers segments 2, 3, 4 and sends selective ACKs: ACK 2, ACK 3, ACK 4.
  - At timeout of segment 1, sender retransmits **ONLY segment 1**!
  - When segment 1 arrives, receiver delivers buffer (0-4) and sends ACK 1.
  - **Total segments sent by $S$ in SR $= 5 + 1 = \mathbf{6\text{ segments}}$.**
  - **Total ACKs sent by $R = \mathbf{5\text{ ACKs}}$ (ACK 0, ACK 2, ACK 3, ACK 4, ACK 1).**
- **In TCP (with Fast Retransmit)**:
  - Receiver sends ACK 1 for segment 0.
  - On segments 2, 3, 4, receiver buffers and sends 3 duplicate ACKs: ACK 1, ACK 1, ACK 1.
  - Sender receives 3 dup ACKs, fast retransmits **ONLY segment 1**.
  - Upon receiving segment 1, receiver generates **cumulative ACK 5**!
  - **Total segments sent by $S = \mathbf{6\text{ segments}}$.**
  - **Total ACKs sent by $R = \mathbf{5\text{ ACKs}}$.**

### Part (ii): Window States at Receiver and Sender for SR (Segment 1 Lost)
- **Sender Window**: `[1, 2, 3, 4, 5]` (Base = 1, packets 2, 3, 4 marked as ACKed, packet 1 unACKed).
- **Receiver Window**: `[1, 2, 3, 4, 5]` (Slot 1 empty/waiting, slots 2, 3, 4 filled with buffered data).

### Part (iii): Link Utilization ($\eta$)
$$\eta = \frac{W \times T_{tx}}{T_{tx} + RTT} = \frac{5 \times 1\text{ ms}}{1\text{ ms} + 10\text{ ms}} = \frac{5}{11} \approx \mathbf{45.45\%}$$

### Part (iv): Number of Timers Required at Sender Side
- **GBN**: **1 Timer** (running for the oldest unacknowledged packet).
- **SR**: **$W$ Timers (5 Timers)** (1 independent timer per unacknowledged packet).
- **TCP**: **1 Retransmission Timer** (for the oldest unacknowledged segment).

## Problem 4: TCP Tahoe vs Reno Congestion Control (Loss of Segment 12)
*(Scan0028 Exam Paper Question 1b)*

**Scenario**:
- Initial $ssthresh = 32\text{ MSS}$.
- Sequence numbers start from 0. Each packet ACKed without delay.
- **Segment 12 is lost**.

### Round-by-Round Execution Trace Table:

```
+-------+-----------+----------------+----------------------+------------------------------------+
| Round | Start cwnd| Start ssthresh | Segments Transmitted | Status / Transition                |
+-------+-----------+----------------+----------------------+------------------------------------+
| R1    | 1         | 32             | 0                    | ACK 0 recvd -> cwnd = 2 (SS)       |
| R2    | 2         | 32             | 1, 2                 | ACK 1, 2 recvd -> cwnd = 4 (SS)    |
| R3    | 4         | 32             | 3, 4, 5, 6           | ACKs recvd -> cwnd = 8 (SS)        |
| R4    | 8         | 32             | 7, 8, 9, 10, 11,     | Seg 12 LOST! Segs 7-11 ACKed       |
|       |           |                | 12 (LOST), 13, 14    | (cwnd grows to 13). Segs 13, 14    |
|       |           |                |                      | cause 2 duplicate ACKs for 11.     |
| R5    | 13        | 32             | 15, 16, 17, 18 ...   | 3rd dup ACK arrives for 11!        |
+-------+-----------+----------------+----------------------+------------------------------------+
```

### Detection of Loss:
- Current $cwnd$ at loss detection $= 13$.
- New threshold: $ssthresh = \lfloor 13 / 2 \rfloor = \mathbf{6\text{ MSS}}$.
- **TCP Tahoe Behavior**:
  - Drops $cwnd = \mathbf{1\text{ MSS}}$.
  - Retransmits segment 12.
  - Enters Slow Start until $cwnd = 6$, then Congestion Avoidance ($cwnd$ grows linearly $+1$ per RTT).
- **TCP Reno Behavior**:
  - Sets $ssthresh = \mathbf{6\text{ MSS}}$.
  - Sets $cwnd = ssthresh + 3 = 6 + 3 = \mathbf{9\text{ MSS}}$.
  - Fast Retransmits segment 12 and enters **Fast Recovery**.
  - On arrival of NEW cumulative ACK acknowledging through segment 18:
    - Reno **deflates** $cwnd$ to $ssthresh = \mathbf{6\text{ MSS}}$.
    - Enters **Congestion Avoidance** directly (never drops to 1).
